### W2-01：明确系统角色

- 按学生、导师、审核与培养管理人员三类 Actor 描述使用目标和业务操作。申请与在读作为学生的业务阶段；复核、组织管理与正式确认作为分别授权的职责。
- 编写权限矩阵，至少覆盖材料提交、规则查看与维护、任务分配、意见复核、整改处理、正式结果确认、档案和画像查看。
- 区分提供意见与确认结论；导师、审核与培养管理人员是否具有某项确认权限，以具体授权为准。智能体接入属于系统能力，正式结论仍由有权限的人员复核确认。

**验证：** 用“学生查看自己的材料”“导师查看负责学生”“仅有复核权限的人员尝试确认结果或组织任务”“其他用户访问无权查看的档案”等场景逐项检查权限矩阵；业务上尚未确定的授权规则列为待确认项。

### W2-02：编写功能树

- 按业务职责拆分模块，再将模块细化为用户或系统能完成的具体功能。四项核心能力、各类用户场景和公共能力均需覆盖。
- 为叶子功能分配 `FR-x.y` 编号。学生端与管理端作为功能入口关联 FR，共用流程保持同一编号；招生、评奖、匹配与帮扶等独立业务分别细化。
- 在功能树文档中保留“FR 编号—功能名称—入口—Actor—原范围编号”的映射。覆盖 `AUD`、`REV`、`ARC`、`PRO`、`STU`、`TEA`、`ADM` 和 `BASE` 条目；`VAL` 条目用于关联双端集成与试点验收。

**验证：** 逐项对照产品范围，检查遗漏、重复功能和无来源的新功能；确认每个叶子节点都能找到对应需求条目。编号确定后保持稳定，调整时保留变更说明。

### 检查点：角色与功能树

业务评审人员核对角色职责、数据范围、模块划分及范围映射，评审意见用于修订需求草案。涉及范围变化的内容确认后再定稿，不自行删减现有功能范围。

### W2-03：编写功能需求与非功能需求

功能需求按以下结构逐条编写；必要时为同一功能拆分子场景。

| 字段 | 要说明的内容 |
| --- | --- |
| 编号与名称 | 与功能树一致的 FR 编号、功能名称及原范围编号 |
| Actor 与前置条件 | 谁发起、需要什么权限、业务记录处于什么状态 |
| 输入 | 数据或材料、必填条件、来源及适用版本 |
| 处理 | 业务规则、权限检查、状态变化、人工处理与 AI 辅助的职责 |
| 输出 | 用户看到的结果、保存的记录、关联的依据与版本 |
| 异常与边界 | 缺材料、证据冲突、规则歧义、解析失败、重复操作及权限限制等适用情况 |
| 验收场景 | 给定条件、执行操作、预期结果；关联相关领域对象 |

优先描述“学生提交—AI 初审—管理端复核—学生补交—确认归档—双端更新成长信息”的闭环，再补齐其余功能。管理端细化规则与流程，学生端复用共用功能；每个叶子功能均需具备需求说明与验收场景。

非功能需求按 `NFR-x` 编号，简要说明性能、安全与权限、数据保护、可靠性、可追溯性、AI 辅助质量、易用性与兼容性、可维护性与扩展性等基本要求。

当前列出待确认的使用规模、部署条件、质量标准和使用环境。具体指标与验证方法在相关条件确定后补充。

**验证：** 核对每个 FR 的正常流程及适用异常；检查非功能要求是否符合双端职责和数据边界，是否将未确定的内容明确列为待确认。

### W2-04：绘制 UML 领域类图

- 从功能需求中识别业务对象，优先检查学生档案、培养计划、培养节点、规则及版本、材料及版本、审核任务、初审意见、复核记录、整改记录、正式结论、成果和画像证据。
- 根据功能树补充申请、评选、匹配、监测与帮扶所需对象；为对象说明关键属性和含义，为关系标注业务语义及端点多重性。
- 在 `domain_model.md` 中保存 Mermaid 类图和对象说明，关联 FR 编号。领域模型描述业务概念；框架、数据库表和部署方式留待工程设计确定。

**验证：** 沿审核闭环检查能否找到每一步产生的记录，能否关联当时使用的规则版本、材料版本、证据和人工处理者；检查同一材料多次补交、意见修正及跨节点使用等情况。再逐项核对其余功能需要的数据与关系。

### 检查点：需求与领域模型

评审时抽取一条完整业务流程，检查“Actor—FR—范围编号—领域对象—验收场景”能否对应；再核对所有范围条目是否都有去向。待确认项应写明影响，交付状态区分草稿、已评审和已确认。

1. 在 README 中增加五份交付文档的导航，更新目录说明；核对角色、功能编号、状态名称和模型关系的一致性。
2. 检查本地文档链接、类图渲染和待提交差异，保留其他人的改动；暂存后运行 `git diff --cached --check`。
3. 按仓库授权约定，在获得明确授权后提交、推送或创建 PR；使用 `docs:` 类型的提交信息，PR 关联对应任务并说明实际完成的验证。
4. 在 GitHub 查看目标分支中的文档、链接和类图，记录评审反馈及处理结果，通过验收后更新 Issue 与 Project 状态。确认提交和推送成功后再记录交付完成。

当前尚无应用构建和测试命令。第二周验证以需求覆盖、权限场景、跨文档一致性、链接和类图检查为主；文档通过检查不代表系统功能已经实现或性能目标已经达到。
