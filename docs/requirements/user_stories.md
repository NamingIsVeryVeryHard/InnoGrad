# 用户故事、验收标准与故事地图

关联任务：[第三周总任务 #13](https://github.com/NamingIsVeryVeryHard/InnoGrad/issues/13)。

**状态：第三周设计草案，待业务评审。** 本文将[角色与权限](actors.md)、[功能需求](functional_requirements.md)和[领域模型](../software/domain_model.md)转为可演示、可验收的用户任务。Release 是建议的实现顺序，不对应课程周次，也不删减既有产品范围。

故事与验收标准的写法参考[客服智能体案例](https://github.com/bettermorn/AIAgent/blob/main/docs/CSAgent_UserStory_AcceptanceCriteria.md)：分别说明角色、功能与价值，再按场景列出 Given / When / Then。对应的[客服演示视频](https://www.bilibili.com/video/BV1KXhR65EAy/)和[示例代码](https://github.com/bettermorn/AIAgent/tree/main/code/CSAIAgent)供后续交互设计参考；本文的业务范围与权限仍以 InnoGrad 需求为准。

## 故事地图

从左至右为业务流程主干，从上至下为交付层次。跨步骤的权限、审计和版本追溯贯穿所有 Release。

| 交付层次 | 明确要求 | 准备与提交 | 检查与复核 | 整改与再核验 | 确认与归档 | 成长与培养管理 |
| --- | --- | --- | --- | --- | --- | --- |
| Release 1：核心闭环 | US-01 适用要求 | US-02 材料版本；US-03 正式提交 | US-04 核对依据；US-05 人工复核 | US-06 补交与新轮次 | US-07 正式确认 | US-08 本人进度与档案；US-09 画像依据 |
| Release 2：体验与节点扩展 | 规则维护与任务组织 | US-10 提交前预审；申请准备 | 更多节点、代办与职责分配 | 画像纠错、档案更正 | 历史与更正版本 | US-11 指导与反馈；US-12 提醒与待办 |
| Release 3：跨业务管理 | 招生、评奖与项目条件 | 申报与成果核实 | 候选与匹配依据 | US-13 预警核实与帮扶 | 按活动授权确认 | 资源配置参考与群体分析 |

Release 1 先用一个节点验证闭环。文档暂以**年度报告**和虚构规则说明流程；首个实际试点节点、材料清单、学校阈值与责任岗位仍待确认。Release 2、3 表中未编号的项目是候选 Epic，需在进入迭代前拆成小故事，不能直接作为已满足 INVEST 的故事验收。其余六类节点、招生、评奖和匹配等仍沿用[功能树](feature_tree.md)的完整范围。

## 故事清单

以下 Given / When / Then 是正式系统的预期验收条件，尚未实现或运行验证。所有故事同时适用 FR-1.2 权限检查、FR-1.3 审计和 FR-1.4 来源追溯；前置业务记录可由预置测试数据准备，无须依赖另一故事的页面才能独立测试。

### US-01 查看本节点适用要求

**用户故事：**

角色：作为一名学生，

功能：我想要查看本人当前节点的材料清单和适用规则，

价值：以便准备正确的材料。

- Release 1；ACT-01；FR-2.2、FR-2.3、FR-11.2。
- 范围：一次查看一个节点；规则编辑和发布另行拆分。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 查看已配置的节点要求
Given 学生有本人节点查看权，节点已关联有效规则版本
When 学生打开节点要求
Then 展示材料清单、截止时间、规则版本与来源
And 区分必交、允许后补和不适用项目

Scenario: 节点没有已确认的适用规则
Given 本人节点尚无已确认的适用规则
When 学生打开节点要求
Then 显示规则待确认和联系入口，不编造清单或通过条件
```

### US-02 保存一份材料的新版本

**用户故事：**

角色：作为一名学生，

功能：我想要上传本人报告并查看材料版本，

价值：以便替换草稿时仍能追溯之前的内容。

- Release 1；ACT-01；FR-4.1、FR-4.2。
- 范围：一份报告的上传、版本与解析反馈；批量导入另行拆分。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 保存修订报告的新版本
Given 学生可编辑本人草稿，已有报告 v1
When 学生上传符合已配置格式与大小限制的修订报告
Then 保存为 v2，保留 v1 及提供者、操作者和接收时间
And 展示该版本的解析状态

Scenario: 拒绝不符合限制的文件
Given 文件不符合已配置的上传限制
When 学生上传文件
Then 拒绝文件并说明具体原因，原有材料保持不变

Scenario: 材料已接收但解析失败
Given 本人报告 v2 已保存，解析任务失败
When 学生查看材料状态
Then 显示解析失败、受限范围和重新上传或联系处理的入口
And 不将未解析内容显示为已完成检查
```

### US-03 正式提交材料包

**用户故事：**

角色：作为一名学生，

功能：我想要确认材料清单后正式提交，

价值：以便获得回执并进入审核流程。

- Release 1；ACT-01；FR-4.3、FR-5.1；相关对象：SubmissionPackage、AuditTask、AuditRound。
- 范围：一个已配置节点的一次提交；规则维护、任务分配为预置条件。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 正式提交符合条件的材料包
Given 节点可提交且必交材料符合提交条件
When 学生确认所用材料版本并正式提交
Then 保存固定材料包、回执和引用规则版本的首轮审核记录
And 任务为待初审，学生端和管理端引用同一任务

Scenario: 必交材料缺失时阻止提交
Given 缺少不允许后补的材料
When 学生尝试正式提交
Then 阻止提交并列明缺项，不创建成功回执

Scenario: 重复发送同一次正式提交请求
Given 同一次提交已成功保存材料包、回执和首轮审核记录
When 学生重复发送该提交请求
Then 返回原回执，不重复创建材料包、任务或审核轮次
```

### US-04 核对初审依据与失败原因

**用户故事：**

角色：作为一名获分配任务的审核人员，

功能：我想要逐项查看初审问题、适用规则和材料证据，

价值：以便判断哪些意见可信、哪些需要人工处理。

- Release 1；ACT-03；FR-5.3、FR-5.4、FR-10.1、FR-10.3。
- 范围：当前任务、当前轮次的意见查看与失败处理；不能直接确认结论。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 展开初审问题的规则与证据
Given 当前轮次初审完成且输出核验通过，审核人员具有查看权
When 审核人员展开一条问题
Then 展示对应材料版本、页码或段落、规则版本与判断理由
And 明确标记 AI 辅助意见和未检查内容

Scenario: 初审失败后重试
Given 当前轮次初审失败，失败原因已记录，处理者有重试权限
When 处理者发起重试且执行获接收
Then 显示新的执行状态，重试记录仍关联同一轮次和固定材料包
And 不创建新审核轮次，不生成正式结论

Scenario: 初审失败后转人工复核
Given 当前轮次初审失败，处理者有转人工权限
When 处理者选择转人工复核
Then 任务进入待复核，并显示失败原因和没有有效 AI 初审结果的说明
And 后续正式确认仍需满足人工复核与确认授权条件
```

### US-05 记录人工复核并发布整改

**用户故事：**

角色：作为一名获分配复核任务的审核人员，

功能：我想要核对并修正初审意见、发布明确的整改要求，

价值：以便学生知道需要补充什么。

- Release 1；ACT-02、ACT-03 按复核及发布权限；FR-5.5、FR-5.6。
- 范围：当前轮次一次复核；正式确认另属 US-07。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 保存人工复核并发布整改
Given 任务待复核且处理者具有复核和整改发布权限
When 处理者说明理由与依据并发布一项整改要求
Then 保存人工意见与原 AI 意见，任务进入整改中
And 学生只看到已发布的整改内容，内部未发布意见不可见

Scenario: 仅有复核权的人员尝试正式确认
Given 人员只有复核权而没有正式确认权
When 人员尝试确认正式结果
Then 请求被拒绝，任务和正式结论不变
```

### US-06 回复整改并补交

**用户故事：**

角色：作为一名学生，

功能：我想要对已发布的整改逐项回复并补交材料，

价值：以便审核人员核验我已解决的问题。

- Release 1；ACT-01；FR-5.6、FR-5.7；RevisionResponse、SubmissionPackage、AuditRound。
- 范围：当前整改的一次补交；不覆盖上一轮材料和意见。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 保存整改回复草稿
Given 本人任务为整改中，已发布整改要求
When 学生保存回复草稿
Then 只保存草稿，不创建正式补交包和新审核轮次

Scenario: 正式提交整改回复与补交材料
Given 回复与补交材料符合提交条件
When 学生正式提交整改回复
Then 回复关联固定补交包，创建下一轮并进入待初审
And 历次材料与意见保留，旧预审报告不能代表新版本结果
```

### US-07 确认正式结论并归档

**用户故事：**

角色：作为一名具有当前节点确认权限的管理人员，

功能：我想要在必需复核完成后确认结论并归档，

价值：以便形成可追溯的正式培养记录。

- Release 1；ACT-02、ACT-03 另授确认权限；FR-5.8、FR-6.3。
- 范围：一个待确认任务；结果类型与会签条件由节点配置决定。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 确认当前轮次并完整归档
Given 任务待确认，必需复核项完成，无未处理整改，确认授权有效
When 确认者核对当前轮次、结论与依据并确认
Then 一并保存正式结论、材料与规则版本、确认者和审计记录
And 仅在上述记录完整保存后，任务显示为已归档

Scenario: 初审期间尝试正式确认
Given 任务仍在初审中
When 请求正式确认
Then 拒绝操作并提示当前状态不允许确认，不生成正式结论

Scenario: 仍有未处理整改时尝试确认
Given 当前任务存在未处理的整改要求
When 请求正式确认
Then 拒绝操作并列出待处理事项，不生成正式结论

Scenario: 确认授权失效
Given 任务待确认，但请求者的确认授权已失效
When 请求正式确认
Then 拒绝操作并提示权限不足，任务和正式结论不变

Scenario: 重复发送同一次确认请求
Given 同一次确认已完整保存，任务已归档
When 确认者重复发送该确认请求
Then 返回已有确认结果，不重复创建正式结论和归档记录
```

### US-08 查看本人进度与归档依据

**用户故事：**

角色：作为一名学生，

功能：我想要看到当前培养进度和已发布的归档依据，

价值：以便明确下一步事项。

- Release 1；ACT-01；FR-6.3、FR-6.4、FR-11.2。
- 范围：本人一个节点和相关档案；不含全院汇总。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 按正式结果展示本人进度
Given 本人一个任务已归档，另一个任务仅完成 AI 初审
When 学生查看进度
Then 已归档节点关联正式结论，另一任务仍显示待复核
And 可打开本人获准查看的历史，不泄露内部意见或他人资料

Scenario: 申请阶段查看培养进度
Given 学生仍在申请阶段，没有在读培养计划
When 学生查看培养进度
Then 显示不适用，不生成虚构的培养记录
```

### US-09 查看画像中的证据与不确定性

**用户故事：**

角色：作为一名学生，

功能：我想要展开本人已发布画像的评价依据和复核状态，

价值：以便理解材料中的表现并发现待补证事项。

- Release 1；ACT-01；FR-7.2、FR-7.3；ProfileSnapshot、CapabilityAssessment、EvidenceRef。
- 范围：一个已发布快照的一条评价；量规设计、计分与更正单独处理。

**验收标准（Given / When / Then 场景）：**

```gherkin
Scenario: 展开已发布评价的依据
Given 本人已发布快照中有一条具备证据的评价
When 学生展开该评价
Then 显示观察事实、证据位置、适用量规版本与人工复核状态
And 明确评价反映材料中的表现，不推断稳定能力

Scenario: 没有足够证据或尚未评价
Given 某维没有足够证据或尚未评价
When 展示该维
Then 显示未评价或待补证，不填零分、不生成无依据总分
```

**验收标准（Given / When / Then 场景）：**

```gherkin

```

## INVEST 与估算准备

| 原则 | 本文的约束 |
| --- | --- |
| Independent 独立 | 尽量按独立用户价值拆分。提交、补交和确认分别为 US-03、06、07，但存在业务前置依赖；团队估算时核对能否分别实现与交付，不能仅因可单独测试就认定完全独立 |
| Negotiable 可协商 | 固定的是价值、权限、版本和可观察结果；布局、通知形式和细节可与用户协商 |
| Valuable 有价值 | 故事句式说明谁受益及解决的问题，技术工作不冒充用户价值 |
| Estimable 可估算 | 已给 Actor、FR、输入边界和验收；对未定规则先做调研，不将未知工作估为零 |
| Small 足够小 | 每条限制为单节点、单任务或单事项；实现前团队再拆分超过一次迭代的故事 |
| Testable 可测试 | 每条至少两个 Given / When / Then 场景，覆盖正常结果与异常或边界 |

US-01、08、09、11、12 以查询或反馈为主，可用预置记录估算；US-02、03、05、06、07 涉及版本、状态或权限，应包含服务端与界面工作；US-04 先做平台接入和失败恢复调研；US-10、13 依赖规则与样本校准。故事点由团队结合实际实现方案估算，本周不填写未经讨论的数字。

## 后续原型范围与评审

交互原型待制作，建议围绕 US-01 至 US-09 的核心闭环组织节点要求、材料提交、审核依据、整改补交、正式确认、档案历史和画像依据等页面。除正常流程外，还应演示缺材料、初审失败、无确认权限和证据不足等状态。原型的具体形式与工具在文档评审后确定。

课程要求的原型交付路径为 `docs/software/prototype`。后续原型只验证交互与流程可行性；真实身份认证、文件解析、模型质量、数据库事务和数据隔离仍需单独验证。

评审需确认：首个试点节点、允许后补的条件、整改发布范围、正式确认岗位和画像量规。按[第三周计划](../../tasks/plan.md)记录反馈；通过课程检查后再进入系统开发。
