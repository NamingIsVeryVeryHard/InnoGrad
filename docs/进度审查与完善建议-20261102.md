当前已形成可运行、数据持久化的首期系统：论文和年度报告申报、版本与原件、Agent 自动归档控制、异常处理、事实画像、研究计划和预警跟进均有实际后端。界面已采用学校风格。

## 优先改进项

### P1：自动通过规则仍缺少完整的业务核验清单

位置：`backend/app/auto_review.py` 的 `assess`，尤其语义检查筛选与文件覆盖判定（27—37 行）。

当前会校验解析和字段检查、至少一项确定性语义检查、引用文字和所有附件覆盖。但没有要求每项指定业务规则都出现在报告中，也没有把“论文状态真实性、作者身份、个人贡献、材料一致性”等规则列为必须逐项响应的固定集合。因此，“每份原件有可核验引用”仍可能被当作满足通过条件，而不能证明业务核验已完整执行。

建议：按材料类型发布不可变的必查规则清单，Agent 逐项返回规则 ID、结论和证据；缺项、重复项、不适用依据不足一律转异常。使用独立标注样本验证误通过、误退回及无法判断比例后，再开展真实试点。

### P1：失败归档事件可能阻塞后续队列

位置：`backend/app/worker.py` 的 `drain` 和 `main`。

`drain` 按时间取最早 pending 事件。如果生成档案或画像持续抛异常，事务回滚，事件再次恢复 pending；主循环只写错误日志，下一轮仍取同一事件。缺少 outbox 事件的重试次数、退避时间和隔离状态，可能导致之后的正常归档长期等待。已有 AI 作业租约/重试机制不等于 outbox 已具备该能力。

建议：新增事件级 attempts、next_retry_at、last_error、failed/dead_letter 状态；单条失败应可隔离并允许后续任务继续。增加“前一事件失败、后一事件仍完成”的验收测试。

### P1：真实 Agent 尚未接入，完整智能审核仍未实测

当前 `.env` 按此前用户选择保持 Agent 待配置。已有测试使用隔离处理器或模拟响应；预置异常报告明确标注模拟。不能据此宣布真实文档语义审核准确率已达标。

建议：接入获准服务，先用合成样本和脱敏材料测试协议、超时、证据引用与失败降级，再开展人工标注对照评测。OCR 也需单独接入和验收。

### P2：预警再次发生时可能仍沿用之前的“已处理”状态

位置：`backend/app/growth.py` 的 `warning_candidates`（目标预警以条目 ID 和截止日期生成键）及 `warnings_for`（按该键套用最后一条处理状态）。

若某计划预警已被标记 resolved/dismissed，之后完成又重新计划，且原截止日期不变，会生成相同预警键，再次套用原来的关闭状态，可能不回到待跟进队列。另外，没有跟进记录的预警在条件消除后不会留下独立的发生/消除历史。

建议：建立独立预警事件表和 occurrence/episode 标识，记录首次发生、最近检测、解除与再次发生；区分“处理意见已记录”和“业务条件已消除”。

### P2：群体画像与前端刷新存在扩容风险

位置：`backend/app/growth.py` 的 `dashboard_data`、`growth-overview`；`backend/app/review_flow.py` 的 `queue`；`frontend/prototype/app.js` 的 `refresh` 和 15 秒轮询。

群体总览逐个学生计算画像，内部反复查询整个授权范围的预警。审核队列先读全部已提交记录再逐一校验权限。前端定时刷新会分页拉取全部材料及版本，再请求多组接口。14 位模拟学生可使用，但不代表百人/千人规模已通过性能验收。

建议：SQL 层先按范围过滤、批量预取资料、一次计算预警并按学生分组；列表返回摘要而非所有历史，详情按需加载；增加服务端分页、条件刷新及规模测试。

### P2：全周期范围与当前首期范围需要在产品上保持一致

目前核心业务是论文和年度报告。开题、中期、预答辩、毕业与学位申请尚未形成完整独立流程；六类材料覆盖也不是正式能力评分。

建议：先完成当前首期流程质量验收，再逐阶段扩展；明确每个阶段的表单、规则、证据、状态和异常处理，不仅新增菜单。
